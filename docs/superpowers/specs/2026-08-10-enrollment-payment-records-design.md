# 選課繳費紀錄架構修正設計

**日期：** 2026-08-10

## 目標

將新增選課時的帳務輸入從 enrollment 舊制欄位改為正式的「繳費紀錄」模型，使一筆繳費可以涵蓋同一季度的一至多門課，同時修正新增選課 RPC 的權限、識別碼相容性、重複送出、錯誤顯示與 modal 無障礙問題。

## 背景

目前 `AddEnrollModal` 可在新增選課時將金額與發票編號寫入 `enrollments.amount` 與 `enrollments.invoice_number`。這些欄位在現行帳務架構中只作為舊資料備援，新資料寫入後會立即被標示為「舊制帳單」。另一方面，現有 `course_receipts` 強制一門課對應一筆收據，無法表示同一張發票同時涵蓋多門課。

目前新增選課 RPC 另有兩個跨層問題：它以 `security definer` 執行卻沒有檢查應用程式角色，因此 viewer 可繞過前端直接呼叫；函式固定以 `bigint` 處理 enrollment ID，也無法兼容正式環境可能使用 UUID 的既有 schema。

## 業務規則

- 一筆 enrollment 代表一位學生在單一季度的選課紀錄。
- 一筆繳費紀錄只屬於單一 enrollment，但可涵蓋其中一至多門課。
- 同一 enrollment 可有零至多筆繳費紀錄。
- 每門課最多屬於一筆繳費紀錄，不支援分期或同一門課多次付款。
- 課程可先建立而不填繳費資料，之後再補登。
- 新建立的繳費紀錄金額必填，必須為 0 或正整數；發票編號選填。遷移前已存在但未記載金額的舊收據仍須保留。
- 使用者介面統一稱為「繳費紀錄」，不顯示「收據群組」等資料建模術語。

## 範圍

本次包含：

- 新的繳費主檔與課程關聯資料模型。
- 既有 `course_receipts` 與可安全判斷之 enrollment 舊制帳務遷移。
- 新增選課時可選填零至多筆繳費紀錄。
- 帳單明細可針對尚未繳費的課程建立一筆涵蓋多門課的繳費紀錄。
- 繳費紀錄金額／發票修改與整筆刪除。
- 新增選課及繳費 RPC 的資料完整性與 editor/admin 授權。
- `AddEnrollModal` 的送出狀態、錯誤顯示和 modal 無障礙修正。
- 移除 `CourseTagPicker` 沒有作用的 `canManage` prop。
- 資料庫、domain、service、component 與 build 驗證。

本次不包含：

- 分期付款。
- 同一門課對應多筆繳費。
- 跨季度共用同一筆繳費。
- 付款退款、折讓或會計傳票模型。
- 自動合併發票編號相同的歷史資料。
- 新增第三方表單或狀態管理套件。

## 資料模型

### `billing_receipts`

繳費主檔包含：

- `receipt_id bigint generated by default as identity primary key`
- `amount integer null check (amount is null or amount >= 0)`
- `invoice_number text null`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

主檔不直接儲存 `enrollment_id`。所屬 enrollment 由關聯課程推導，可避免新資料表依賴不同環境中 UUID／bigint 不一致的 enrollment ID 型別。`amount` 只為無損保留舊空白收據而允許 null；所有新建 RPC 都必須拒絕空金額。

### `billing_receipt_courses`

繳費與課程的關聯包含：

- `receipt_id bigint not null references billing_receipts(receipt_id) on delete cascade`
- `course_id bigint not null references courses(course_id) on delete restrict`
- `primary key (receipt_id, course_id)`
- `unique (course_id)`

`unique (course_id)` 保證每門課最多只有一筆繳費。資料庫約束或受控 RPC 必須驗證同一 `receipt_id` 的所有課程具有相同 `courses.enrollment_id`。空繳費主檔不合法；建立主檔與至少一筆關聯必須在同一交易完成。

直接新增、更新或刪除這兩張表的權限不授予一般 client。所有異動經過鎖定 `search_path`、完整限定物件名稱並內建角色檢查的受控 security-definer RPC，避免 client 繞過跨表不變量。RPC 仍以呼叫者 JWT 的 `app_metadata.app_role` 作授權依據。

## 前端資料形狀

表單內使用以下資料形狀：

```js
{
  season: '第十六季',
  reg_type: '續',
  pre_test: '',
  post_test: '',
  refunded: false,
  refund_info: '',
  courses: ['A 課程', 'B 課程', 'C 課程'],
  paymentRecords: [
    {
      localId: 'client-generated-stable-id',
      courseNames: ['A 課程'],
      amount: '1000',
      invoiceNumber: 'AB12345678',
    },
    {
      localId: 'client-generated-stable-id',
      courseNames: ['B 課程', 'C 課程'],
      amount: '2000',
      invoiceNumber: '',
    },
  ],
}
```

`localId` 只供 React 穩定渲染，不送入資料庫。service 將每筆資料正規化為 RPC 使用的 `course_names`、整數 `amount` 與 nullable `invoice_number`。

## 新增選課互動

`AddEnrollModal` 先讓使用者選擇本季課程，繳費區預設為空，因此建立選課不要求立即付款。

按下「新增繳費紀錄」後：

1. 顯示目前已選、但尚未分配給其他繳費紀錄的課程。
2. 使用者選擇一至多門課。
3. 使用者輸入必填總金額及選填發票編號。
4. 可重複新增其他繳費紀錄，直到所有課程均已分配，或保留部分課程為未繳費。

同一門課不能出現在兩筆繳費紀錄。若從主選課清單移除已分配課程，表單同步將它從尚未儲存的繳費紀錄移除；繳費紀錄因此沒有課程時，一併移除該筆草稿。

送出期間禁止再次送出、點擊遮罩關閉、按取消或按 Esc 關閉。成功後呼叫 `onRefresh` 並關閉；失敗時保留所有欄位，將可處理訊息顯示在 modal 內。

## 後續補登與帳單明細

日後新增 B 課程時，使用者先透過選課編輯功能將 B 加入 enrollment，再從帳單明細的「新增繳費紀錄」選取 B，或同時選取多門尚未繳費的課程。

帳單明細依繳費主檔顯示：

- 涵蓋課程標籤。
- 總金額。
- 發票編號。
- editor/admin 可使用的編輯與刪除操作。

編輯只修改金額與發票編號。若課程歸屬錯誤，使用者刪除整筆繳費紀錄後重新建立；刪除後原課程重新成為可建立繳費的課程。viewer 僅可讀取。

## RPC 與授權

`create_enrollment_with_courses` 改為接收選課欄位、`p_course_names text[]` 與 `p_payment_records jsonb`。每筆 payment record 包含 `course_names`、`amount` 與 `invoice_number`。

RPC 必須：

- 使用鎖定 `search_path = ''` 且完整限定資料庫物件名稱的 `security definer`；不依賴函式擁有者身分作應用程式授權。
- 在函式開頭驗證 `current_app_role()` 為 `editor` 或 `admin`。
- 驗證學生存在、季度有效、至少一門課、課程名稱有效且不重複。
- 驗證每筆繳費至少一門課、金額合法、課程屬於本次選課且未被重複分配。
- 在單一交易建立 enrollment、courses、billing receipt headers 與 course links。
- 發生任何錯誤時完整回滾。
- 將建立後的 enrollment ID 轉成 `text` 回傳，兼容 UUID 與 bigint 環境。
- 明確撤銷舊函式簽章的 execute 權限，避免 client 繼續呼叫缺少授權檢查的版本。

另提供建立、修改及刪除繳費紀錄的 RPC。建立 RPC 接受一至多個 `course_id`，驗證所有課程屬於同一 enrollment 且尚未有繳費。修改 RPC 只接受 `receipt_id`、金額與發票編號。刪除 RPC 移除主檔並由外鍵級聯清除關聯。

viewer、editor、admin 可讀取帳務資料。mutation RPC 的 execute 可授予 `authenticated`，但函式必須依呼叫者 JWT 拒絕 viewer，只有 editor/admin 能完成異動。UI 權限只控制可見操作，資料庫函式內的角色檢查才是寫入安全邊界。

## 既有資料遷移

遷移採擴充、切換、清理三階段：

1. 建立新資料表、索引、約束、RLS、RPC 與測試。
2. 回填資料並讓 dashboard 改讀新模型。
3. 驗證正式資料後，才停用並移除舊的 `course_receipts` 寫入路徑。

回填規則：

- 每筆既有 `course_receipts` 建立一筆新的 `billing_receipts`，並關聯原本的單一課程；即使發票編號相同也不自動合併。金額為 null 的舊收據照原值保留，但 UI 將它標記為未記載金額。
- enrollment 有非空舊制金額、至少一門課、且完全沒有既有課程收據時，建立一筆涵蓋該 enrollment 全部課程的繳費紀錄；成功後清除已轉換的舊制欄位。
- 只有發票編號而沒有金額的舊資料不符合新規則，保留在唯讀「舊制帳單」區。
- 同時存在 enrollment 舊制帳務與課程收據的資料具有歸屬歧義，不自動轉換或清除舊欄位。
- 沒有課程的 enrollment 不建立繳費紀錄。

遷移需比對轉換前後的收據數、總金額、發票編號及課程關聯，並保留能回復的清理階段，不在初次部署直接破壞舊資料。

## 元件與模組邊界

- `AddEnrollModal.jsx`：modal、基本 enrollment 表單、送出 orchestration。
- `PaymentRecordsEditor.jsx`：繳費紀錄草稿、可選課程、金額與發票欄位。
- `domain/enrollmentPayments.js`：純函式驗證、正規化與課程分配檢查。
- `services/enrollmentService.js`：新增 enrollment 與初始繳費的 RPC adapter。
- `services/billingReceiptService.js`：建立、修改、刪除繳費紀錄的 RPC adapter。
- `EnrollmentBillingDetailModal.jsx`：繳費列表、補登、修改與刪除流程。
- `domain/enrollmentBilling.js`：從查詢資料建立穩定 UI shape 與季度帳務摘要。

`CourseTagPicker` 繼續只負責課程選取。未被元件使用的 `canManage` prop 從定義與呼叫端移除，不將它誤當成權限邊界。

## 驗證與錯誤處理

前端與 RPC 都驗證相同的不變量；RPC 是最終權威。

- 季度無效、沒有課程、繳費沒有課程、金額空白或格式錯誤時不送出。
- 課程重複分配、跨 enrollment、已存在繳費或 stale ID 由 RPC 拒絕。
- 服務將已知錯誤碼轉成穩定中文訊息，不直接向使用者暴露資料庫細節。
- mutation 使用同步 ref 防止同一 render frame 內重複觸發，並以 state 呈現送出中 UI。
- RPC 失敗時保留表單資料；成功後才重新整理與關閉。

## Modal 無障礙

- modal 容器使用 `role="dialog"`、`aria-modal="true"` 與 `aria-labelledby`。
- 關閉按鈕具有明確 `aria-label`。
- 開啟後將焦點移至適當的第一個控制項。
- Tab 焦點保留在 modal 內，關閉後回復到觸發元素。
- 非送出中狀態支援 Esc 關閉。
- 錯誤區使用 `role="alert"`。
- 所有 label 與輸入欄位以穩定且不重複的 ID 關聯。

## 測試策略

### 資料庫

- viewer 無法執行新增選課或帳務 mutation RPC；editor/admin 可以。
- 新增 enrollment 可包含零筆、一筆或多筆繳費紀錄。
- 一筆繳費可關聯一門或多門同 enrollment 課程。
- 相同課程重複分配及跨 enrollment 關聯會被拒絕並完整回滾。
- 新增或修改時，金額空白、負數、小數與超出安全範圍的值會被拒絕；既有 null 金額可在遷移後被讀取。
- 舊 `course_receipts`、可判斷的 enrollment 舊制資料及模糊資料均按遷移規則處理。

### Domain 與 service

- 表單資料正規化為穩定 RPC payload。
- 未繳費課程不產生空 receipt。
- 相同課程不能出現在兩筆繳費紀錄。
- 金額與發票正規化沿用同一套純函式規則。
- 已知 RPC 錯誤會映射為穩定訊息。
- 多門課共用一筆收據時，季度摘要只計算一次金額與發票。

### Components

- 不填繳費仍可建立選課。
- 一門課一筆繳費、多門課共用一筆繳費及同季多筆繳費均可輸入。
- 移除課程會同步更新尚未儲存的繳費草稿。
- 連續送出只呼叫一次 service。
- 錯誤保留所有輸入並在 modal 顯示。
- 成功後只呼叫一次 refresh 與 close。
- dialog 名稱、焦點、Esc 與送出中禁止關閉行為正確。
- 帳單明細只提供尚未繳費的課程，並以一筆金額顯示多門課收據。

## 驗證與發布

實作完成後依序執行：

1. Supabase pgTAP／資料庫 migration 測試。
2. `AddEnrollModal`、繳費 editor、billing domain 與 service 的定向 Vitest。
3. 完整 `npm test`。
4. `npm run lint`。
5. `npm run build`。
6. editor、viewer 帳號的手動 smoke test。

資料庫擴充與回填先在測試環境驗證。正式環境先套用相容 migration，再部署讀取新模型的 dashboard；確認新舊筆數、金額與關聯後才執行舊路徑清理。

## 成功標準

- 使用者可在新增選課時選擇不填繳費，或建立一至多筆各自涵蓋一至多門課的繳費紀錄。
- 一門課永遠不會被計入兩筆繳費，且一筆繳費不會跨季度。
- 後續新增課程可以補登新的繳費紀錄。
- viewer 無法透過 UI 或直接 RPC 寫入。
- 新增流程不會因重複點擊產生競態提示或重複請求。
- 既有可確定歸屬的帳務資料無損轉換，模糊資料不被猜測或刪除。
- 所有資料庫測試、Vitest、lint 與 production build 通過。
