# 同一期多張報名表資料層級設計規格

## 目的

現行系統以 `enrollments` 表示「一位學員在一個期別的報名」，並以
`unique (student_id, period)` 防止同一人同一期出現重複報名。這個限制應保留，
因為人數、期別與退費統計都以這個層級為基礎。

實際作業可能在同一期收到同一學員的多張紙本報名表。每張表可能包含不同課程、
費用、收據 No.、經手人、報到日期、備註與退費狀態。現行費用欄位直接位於
`enrollments`，只能保存一組資料，第二張表會覆蓋第一張表。

本設計在 `enrollments` 與課程／帳務資料之間新增「報名表」層級，使一筆期別報名
可以包含多張可獨立編輯、退費與稽核的報名表。

## 核心業務規則

1. 同一學員、同一期仍只有一筆 `enrollments`。
2. 一筆 enrollment 可以有一至多筆 `enrollment_forms`。
3. 每門課屬於一張報名表；同一期不得重複加入相同課程。
4. 每張報名表各自保存課程、費用、收據、經手人、報到日期、備註及退費狀態。
5. 只退其中一張表時，其他表與其課程仍維持有效。
6. 學員人數以 enrollment 去重；報名表數、課程數與收入則由各表彙總。
7. 既有資料在遷移時自動建立為每筆 enrollment 的「第 1 張報名表」，使用者不需重填。

## 資料模型

```text
students
└── enrollments（學員 + 期別，維持唯一）
    └── enrollment_forms（每張紙本報名表）
        ├── courses（該表所選課程）
        └── billing_receipts（預繳／正式收據）
            └── billing_receipt_courses（既有收據與課程關聯）
```

### `public.enrollment_forms`

新增資料表，欄位如下：

- `form_id bigint generated by default as identity primary key`
- `enrollment_id bigint not null`，外鍵連到 `enrollments`，刪除 enrollment 時 cascade
- `form_sequence integer not null`，同一 enrollment 內顯示為第 1、2、3 張
- `reg_type text`
- `tuition_fee integer`
- `materials_fee integer`
- `membership_fee integer`
- `handled_by_name text`
- `handled_by_user_id uuid`
- `handled_by_account text`
- `reported_on date`，使用者所稱的報到日期
- `notes text`
- `refunded boolean not null default false`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

金額欄位使用非負整數 check constraint。`(enrollment_id, form_sequence)` 必須唯一，
另建立 `unique (form_id, enrollment_id)` 供課程的複合外鍵引用，並為 `enrollment_id`
建立索引，以支援巢狀查詢與 cascade。

### 課程歸屬

`courses` 新增 `form_id bigint`。遷移會先為每筆既有 enrollment 建立預設表，
再將課程回填到該表，最後把 `form_id` 設為 not null。

第一階段保留既有的 `courses.enrollment_id`，以降低一次性切換風險；資料庫以
複合外鍵確保 course 的 `form_id` 與 `enrollment_id` 指向相同 enrollment，避免資料漂移。
既有 `unique (enrollment_id, course_name)` 保留，因此同一期跨兩張表仍不能重複選同名課程。

### 收據歸屬與帳務單一來源

`billing_receipts` 新增：

- `form_id bigint not null`，外鍵連到 `enrollment_forms`
- `receipt_kind text not null`，限制為 `prepaid` 或 `formal`

同一張表每種收據最多一筆，以 `unique (form_id, receipt_kind)` 保護。收據的金額與
No. 以 `billing_receipts.amount`、`billing_receipts.invoice_number` 為唯一帳務來源：

- 預繳金額與 No. 存在 `prepaid` 收據。
- 正式收據金額由該表的學費、教材費、會友費加總，No. 存在 `formal` 收據。
- 金額為 0 且 No. 為空時，不建立該種收據。

既有 `billing_receipt_courses` 暫時保留，報名表的收據會連結該表所有課程；所有新增與
編輯皆經交易型 RPC 同步維護，不允許前端分開更新表單欄位與收據，避免目前
`enrollments` 欄位和收據紀錄不一致的問題。

`enrollments` 上既有的費用、收據、辦理資訊與 `refunded` 欄位在資料回填後不再作為
畫面或統計來源。第一階段保留欄位供相容與回滾，待新流程穩定後再以獨立清理工作移除。

## 寫入流程與 RPC

新增交易型 RPC 作為唯一寫入入口，前端不直接對多張相關資料表分段寫入。

### 新增報名表

1. 依 `student_id + period` 查找 enrollment。
2. 若不存在，先建立 enrollment；若已存在則沿用，不再回報重複期別錯誤。
3. 鎖定該 enrollment，計算下一個 `form_sequence`，避免同時新增造成序號碰撞。
4. 建立 enrollment form。
5. 驗證並建立該表課程。
6. 依輸入建立預繳與正式收據，並連結該表課程。
7. 任一步驟失敗時整筆交易回滾。

新增會員的初次報名與既有會員的加選流程都使用相同的「建立 enrollment + form」領域規則，
避免兩套 RPC 再次產生行為差異。具權限使用者的身分以伺服端驗證後的
`app_metadata.app_role` 判定；稽核帳號與 user id 由登入狀態寫入，不接受前端偽造值。

### 編輯與退費

- 編輯以 `form_id` 為單位，同一交易更新表單欄位、課程與收據。
- 移除已被收據關聯的課程時，由 RPC 一併調整關聯；不留下孤兒資料。
- 退費以 form 為單位切換 `refunded`，不修改其他表。
- 最後一張有效表退費後，enrollment 仍保留供歷史查詢，不自動刪除。
- 實體刪除沿用管理權限及確認流程；一般作業優先使用退費狀態保留稽核紀錄。

## 前端操作設計

### 新增流程

- 新增選課時輸入學員與期別。
- 若該期 enrollment 不存在，建立第 1 張表。
- 若已存在，畫面提示「此學員已有本期報名，將新增第 N 張報名表」，並顯示既有課程，
  讓使用者避免誤選重複課程。
- 使用者確認後才提交，不建立第二筆 enrollment。

### 顯示與編輯

- 歷年選課以期別為外層卡片，內部依「報名表 1、報名表 2」分組。
- 每組顯示各自課程、預繳／正式費用、收據 No.、經手人、報到日期、備註與退費標記。
- 「新增報名表」、「編輯」與「退費」操作都作用於明確的 `form_id`。
- 期別摘要顯示有效表的課程與收入合計；退費表仍可展開查看但不計入有效收入。

Excel／CSV 會員匯入目前只處理會員主檔，不在本功能中增加報名表匯入規則。Excel 匯出則將
一張報名表輸出為一列，重複顯示學員與期別，使兩張紙本的資料可被完整還原。

## 驗證與錯誤處理

- 課程不得為空白，且同一期不可重複同名課程。
- 金額只能是 null 或非負整數。
- 收據 No. 移除前後空白；本階段不新增全域唯一限制，以免既有資料衝突。
- `reported_on` 必須是有效日期。
- 新增／編輯時若 enrollment 或 form 已被其他操作修改，RPC 回傳可辨識錯誤，前端保留輸入並提示重新載入。
- RLS 與 grants 延續現有角色模型；新表必須啟用 RLS，policy 使用既有角色 helper，並以
  `(select public.current_app_role())` 形式避免逐列重算。
- 所有外鍵欄位建立索引；migration 完成後執行 Supabase advisors，修正 error 與必要 warning。

## 統計規則

- 期別學員數：有效 enrollment 的 `student_id` 去重，不因多張表增加。
- 報名表數：該期 form 數量，可另行顯示，不取代學員數。
- 課程數：未退費 form 下的 course 數量。
- 收入：未退費 form 的正式費用合計。
- 預繳：未退費 form 的 prepaid receipt 金額合計。
- 部分退費：只排除被退費 form 的課程與金額；同 enrollment 其他表照常計算。

## 資料遷移

1. 建立 `enrollment_forms`、constraints、indexes 與 RLS。
2. 每筆既有 enrollment 建立 sequence 1 的預設 form，複製報名類型、費用、辦理資訊、
   備註及退費狀態；既有 `handled_on` 明確轉入 `reported_on`，作為報到日期。
3. 將既有課程回填 `form_id`。
4. 依課程關聯把既有 receipts 歸到該預設 form；無法唯一判定的異常資料使 migration 失敗，
   不以猜測方式繼續。
5. 加入 not-null、複合外鍵與收據唯一約束。
6. 更新 RPC、查詢及前端後，停止讀寫 enrollment 上的舊表單欄位。

整個 migration 必須可在現有資料快照上以單一交易完成。正式套用前先在 local Supabase
執行 reset、pgTAP、lint 與 advisors，並以遷移前後筆數及金額總和檢查資料守恆。

## 測試與完成條件

### 資料庫測試

- 同一學員同一期連續新增兩張表成功，但只有一筆 enrollment。
- 兩張表分別保存不同課程、費用、收據、經手人、日期與備註。
- 同一期跨表加入重複課程被拒絕。
- 單張表退費不影響另一張表。
- RPC 任一步驟失敗時不留下 form、course 或 receipt 半成品。
- 無權限角色不能建立、修改或退費。
- 既有資料遷移後，每筆 enrollment 至少一張表，課程與帳務總額不變。

### 前端測試

- 同一期第二次新增時顯示追加表單提示，提交後產生「報名表 2」。
- 期別卡片能分組顯示兩張表及各自欄位。
- 編輯其中一張表不改變另一張表。
- 單張表退費後，摘要與統計只扣除該表。
- 新增或儲存失敗時保留輸入內容並顯示可理解訊息。
- 匯出後兩張表分列且資料完整。

### 回歸驗證

- 全部 Vitest 測試通過。
- 全部 pgTAP 資料庫測試通過。
- ESLint、production build、Supabase database lint 與 advisors 通過既定門檻。
- 手動驗證：一位學員同一期建立兩張表，各兩門不同課與不同 No.，再只退其中一張。

## 不在本次範圍

- 不解除 `unique (student_id, period)`。
- 不支援同一張表多張同種類分期收據。
- 不新增紙本影像上傳或掃描辨識。
- 不更動會員 Excel／CSV 匯入格式。
- 不在同一 migration 直接刪除 enrollment 的舊帳務欄位；清理另案處理。
