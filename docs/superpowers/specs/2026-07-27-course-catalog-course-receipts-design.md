# Course Catalog and Per-Course Receipts

## Goal

Replace free-text course entry with selectable course tags backed by a managed course catalog, and let staff create at most one editable receipt for each course in an enrollment.

## Scope

- Add a formal `course_catalog` table and seed it from distinct existing `courses.course_name` values.
- Replace free-text course entry in enrollment creation and editing with a reusable tag picker.
- Add course-catalog management beside the tag picker so authorized staff can add or deactivate options.
- Add per-course receipts to the enrollment billing detail modal.
- Preserve existing enrollment history, inactive course names, and legacy enrollment-level billing.
- Keep CSV/Excel import and export behavior unchanged.
- Do not add course renaming, receipt deletion, installment payments, or more than one receipt per enrolled course.

## Data Model

### Course catalog

Create `public.course_catalog` with:

- `course_catalog_id bigint generated by default as identity primary key`
- `course_name text not null`
- `active boolean not null default true`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Course names are trimmed before storage. A unique normalized index prevents duplicate names that differ only by surrounding whitespace or letter case.

The migration seeds one active catalog row for every distinct non-blank name already present in `public.courses`.

Deleting a catalog option in the UI is a soft deletion that sets `active = false`. Historical rows in `public.courses` remain unchanged. Adding a name that already exists but is inactive reactivates that row rather than creating a duplicate.

### Course receipts

Create `public.course_receipts` with:

- `receipt_id bigint generated by default as identity primary key`
- `course_id bigint not null references public.courses(course_id) on delete cascade`
- `amount integer`
- `invoice_number text`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`
- `unique (course_id)`
- a check constraint requiring `amount` to be null or a non-negative integer

The unique `course_id` constraint guarantees at most one receipt per enrolled course. Both billing fields are optional. The existence of a `course_receipts` row represents an added receipt even when both optional fields are blank.

### Existing enrollment billing

The existing nullable `enrollments.amount` and `enrollments.invoice_number` columns remain for legacy compatibility.

During migration:

- When an enrollment has exactly one course and either legacy billing field is populated, create that course's receipt and clear the copied legacy billing fields.
- When an enrollment has zero or multiple courses, retain its legacy billing fields unchanged.
- Multi-course legacy billing is never divided automatically because the database cannot infer the correct allocation.

The migration must be idempotent for catalog seeding and receipt copying.

## Authorization and RLS

- Authenticated `viewer`, `editor`, and `admin` roles can select the catalog and course receipts.
- `editor` and `admin` roles can add or reactivate catalog entries and insert or update course receipts.
- Catalog deactivation is allowed to `editor` and `admin`, matching the existing `canEditEnrollment` UI permission.
- Receipt deletion is not exposed through the UI.
- Database RLS is authoritative; the UI permission checks only control available interactions.

## Course Selection

Create one reusable course-tag picker for both `AddEnrollModal` and `EnrollmentEditForm`.

- Active catalog courses appear as clickable tags.
- Clicking an unselected tag selects it; clicking a selected tag deselects it.
- The submitted course list contains catalog names rather than hand-entered text.
- At least one selected course remains required for creating an enrollment, matching the existing enrollment requirement.
- Existing inactive or legacy course names remain visible and selected while editing an old enrollment.
- If an existing course already has a receipt, its selected tag is locked against removal so editing cannot cascade-delete billing history.
- Newly selected courses create new `public.courses` rows.
- Deselected courses without receipts are removed.
- Unchanged selections retain their existing `course_id`; editing must not delete and recreate all course rows.

The picker includes a `管理課程` action for users with `canEditEnrollment`. The management dialog:

- Lists active and inactive catalog entries.
- Adds a trimmed name or reactivates the matching inactive entry.
- Deactivates active entries after confirmation.
- Does not rename catalog entries.
- Refreshes the picker immediately after a successful change.

Viewers can see selected course tags in read-only contexts but cannot open catalog management.

## Per-Course Receipt Interaction

The enrollment billing modal replaces the single editable enrollment-level billing form with a receipt section.

- Existing course receipts are shown as rows containing course name, amount, invoice number, and an `編輯` action.
- `新增收據` expands tags for courses in the selected enrollment that do not yet have a receipt.
- Clicking an available course tag selects that enrolled course and opens its receipt editor; course names are never typed.
- Amount and invoice number may both remain blank.
- Saving creates the missing receipt or updates the existing receipt and keeps the modal open.
- Pending saves disable duplicate submission.
- Once every enrolled course has a receipt, the add action is disabled with a clear explanation.
- A viewer sees receipt rows and legacy billing but no add, edit, or save actions.

The course selection is inherently scoped to the exact enrollment opened in the modal. Catalog courses that are not part of that enrollment are not eligible for billing.

## Legacy Billing Display

When retained legacy billing exists, the modal shows a separate read-only `舊制帳單` block containing its amount and invoice number.

The enrollment history table summarizes billing as follows:

- If the enrollment has one or more course receipts, display the sum of non-null receipt amounts and the distinct non-blank receipt invoice numbers.
- If it has no course receipts, fall back to the legacy enrollment amount and invoice number.
- A receipt set with only null amounts displays `--` rather than zero.
- Multiple invoice numbers are displayed as separate compact values, not concatenated into an editable string.

Legacy billing is not added to the per-course receipt sum, preventing accidental double counting while manual allocation is still incomplete.

## Data Loading and Compatibility

The dashboard enrollment query loads enrolled course rows together with their optional receipt.

The dashboard's normalized enrollment object keeps:

- `courses`: the existing array of course-name strings used by timelines, filters, trends, imports, and exports.
- `courseDetails`: an array of `{ courseId, courseName, receipt }` for course selection and billing.
- Existing enrollment-level `amount` and `invoice_number` fields for legacy display.

Keeping `courses` as strings avoids unrelated rewrites across current consumers. Receipt summaries are derived from `courseDetails` in a pure domain helper so table and modal rules share one tested implementation.

## Error Handling

- Catalog load failures show an inline retry state and do not fall back to free-text entry.
- Duplicate catalog creation resolves to the existing normalized entry; an inactive match is reactivated.
- Catalog mutations preserve the open enrollment form and its selected tags.
- Receipt save failures keep the editor open and preserve the entered values.
- Invalid negative, decimal, or unsafe amounts are rejected before a Supabase write.
- A stale duplicate receipt insertion is surfaced as an already-existing receipt, followed by a refresh that opens the existing row.
- A course with an existing receipt cannot be removed from an enrollment through the tag picker.
- Missing or stale enrolled-course IDs prevent receipt creation and show a reload message.

## Testing

### Database

- Catalog seeding produces one normalized row per distinct historical course name.
- Catalog uniqueness rejects normalized duplicates.
- Catalog deactivation does not change historical `courses` rows.
- Receipt uniqueness permits only one row per `course_id`.
- Optional receipt fields and non-negative amount constraints behave as specified.
- Single-course legacy billing migrates to a receipt and is cleared from the enrollment.
- Multi-course legacy billing remains on the enrollment.
- RLS allows reads for all application roles and mutations only for editor/admin roles.

### Services and domain

- Catalog list, add/reactivate, and deactivate operations use normalized names.
- Enrollment creation accepts selected course names without parsing comma-separated input.
- Enrollment editing diffs course selections, preserves unchanged `course_id` values, and refuses to remove a course with a receipt.
- Receipt create/update payloads contain only the enrolled `course_id`, amount, and invoice number.
- Billing summaries total available receipt amounts, deduplicate invoice numbers, and fall back to legacy billing only when no course receipt exists.

### Components

- Add and edit forms select and deselect course tags without a free-text course input.
- The management dialog adds, reactivates, and deactivates catalog entries without clearing form selections.
- Inactive historical courses remain visible while editing.
- Courses with receipts cannot be deselected.
- The billing modal only offers unreceipted courses from the selected enrollment.
- Adding a blank receipt is valid; subsequent edits update the same receipt.
- Viewer interactions remain read-only.
- Save failures preserve values, and successful saves refresh data while keeping the modal open.
- The history table renders receipt totals/invoices and the legacy fallback correctly.
